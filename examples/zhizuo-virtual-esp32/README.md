# 虚拟 ESP32 —— 智座（`D:\MAX_xiangmu`）设备模拟器

> **一句话**：用**真网络**冒充一台 ESP32 传感器设备，让智座在没有硬件的情况下被端到端驱动。

---

## 1. 为什么需要它（以及它和智座自带模拟器的分工）

智座**自己就有一个模拟器**（`app.py` 的 `_build_sensor_simulator()`），但它是**进程内**的 ——
直接调状态机回调，**完全绕过 HTTP、设备注册、配置下发**。所以两者测的不是一回事：

| | 智座自带模拟器 | **本脚本** |
|---|---|---|
| 位置 | 进程内 | **进程外** |
| 走 HTTP？ | ❌ 直接调回调 | ✅ **真网络请求** |
| 测设备注册 / 配置下发 | ❌ | ✅ |
| 测 `ir_active_high` 电平翻译 | ❌ | ✅ |
| 测在线判定（`last_seen`） | ❌ | ✅ |
| 测状态机逻辑 | ✅ | ✅（顺带） |

**⇒ 互补，不重复。** 它测"状态机对不对"，本脚本测"**设备接得进来吗**"。

---

## 2. 它严格照接口契约办事

这三条都是智座接口的**真实约定**，不是我们编的：

1. **开机注册** —— `POST /api/sensor/device/register {device_id}`
   新设备自动登记（`is_new`），返回下发配置
2. **配置下发免重烧** —— `GET /api/sensor/device_config?device_id=`
   面板改完配置，设备周期拉取即生效。本脚本从配置里取
   `ir_active_high` / `report_interval_ms` / `sensor_type` / `distance_threshold_cm`
3. **周期上报** —— `POST /api/sensor/report {seat_id, ir_front, ir_back}`

### ⚠️ 两个容易做错、且**都不会报错**的地方

**① `ir_active_high` 必须照做。**
它决定"遮挡时读到 1 还是 0"。本脚本的入参是**物理遮挡**，把它翻译成原始电平是
**设备侧**的责任。搞反的症状是**"人坐下反而释放"**，而且**不报任何错**。
→ `VirtualEsp32._raw()` 是唯一做这个翻译的地方。

**② 释放需要连续 2 次空**（`seat.consecutive_empty >= 2`）。
真机就是这样，所以场景里**必须真的多报几次空**，只报一次**不会**释放。
→ 场景写成 `(front, back, 重复次数)` 三元组，把这条编码进去，
  免得误以为"系统坏了"。

## 3. 用法

```bash
# 前提：智座在跑（python app.py 127.0.0.1 5800），且该 device_id 已在面板上绑定了座位
python virtual_esp32.py --server http://127.0.0.1:5800 \
    --device-id 38:3E:51:6F:8E:00 --scenario sit-then-leave
```

**预设场景**（`--scenario`）：

| 场景 | 读数序列 | 用途 |
|---|---|---|
| `sit-then-leave` | 双遮挡 ×2 → 双空 ×3 | 坐下再离开（走完整状态机） |
| `sit` | 双遮挡 ×3 | 只坐不走 → 应转 `occupied` |
| `leave` | 双空 ×3 | 只走不坐 → 应释放回 `free` |
| `one-beam-only` | 单束遮挡 ×3 | **交叉校验**：单束不该判定为有人 |
| `flicker` | 双遮挡 → 单束 → 双遮挡 | 抖动干扰 |

`--repeat N` 可整轮重复。

**只依赖标准库**（`urllib`），不需要 `requests` ——
真机固件也不会带一堆依赖，保持"它就是个瘦客户端"这件事本身重要：
**协议要能在最小实现上跑通。**

## 4. 实测结果（2026-10-08）

对智座（`D:\MAX_xiangmu`，本地实例，MySQL+Redis 均为本机已在运行的服务）实测：

```
[1/3] 注册 38:3E:51:6F:8E:00
      is_new=False  config={"seat_id": 6, "seat_label": "A-4", "floor_id": 3,
                            "ir_active_high": true, "report_interval_ms": 1000,
                            "sensor_type": "ultrasonic", "distance_threshold_cm": 50}
[2/3] 拉配置 ✓
[3/3] sit-then-leave ✓
```

**状态机确实响应了**（不是"跑完没报错"就算数）：

| | `status` | `ir_front/back` | `consecutive_empty` | `sensor_data` 行数 |
|---|---|---|---|---|
| 跑 `sit` 之前 | `free` | 0 / 0 | 3 | 234 |
| 跑 `sit` 之后 | **`occupied`** | **1 / 1** | **0** | **237** |
| 跑 `leave` 之后 | `free` | 0 / 0 | 3 | — |

`last_scan_time` 也被刷新（在线判定依赖它）。
**测试后已把 seat 6 还原到初始状态**（`free`，`0/0`，`consecutive_empty=3`），
并停掉了本地智座实例。

## 5. 它**不**做的事（别误读）

- ❌ **没有接进 DSH 沙盒插件** —— 这是**独立脚本**，不是插件的设备类。
  插件的 SSOT 里看不到这台设备，3D 场景里也不会出现它。
- ❌ 不模拟超声波/红外的**物理过程** —— 它按场景直接给出"遮挡/未遮挡"。
  （`sensor_type=ultrasonic` 时真机测的是距离，本脚本不建模距离→遮挡的换算。）
- ❌ 不做多设备编排 —— 一台设备一个进程。多座位要自己起多个。

**⇒ 它证明的是"这条路走得通"，不是"插件已经支持这一类设备"。**
要不要把「网络设备模拟器」做成插件的**第二类虚拟硬件**（与现在的 I2C 协议虚拟化并列），
是一个**架构决定**，见 `docs/06` §5 与 §6。
