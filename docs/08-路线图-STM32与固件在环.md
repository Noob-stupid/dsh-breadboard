## 0. 别误解这一份：做完 ABC ≠ 「变成通用硬件驱动」

用户问过一句「路线图做了就相当于能驱动硬件了是吧」—— **要看是哪种"驱动"**，三句话分清：

| 「驱动硬件」指 | 哪条线 | 做完之后 |
|---|---|---|
| 让插件**操作真板子**（烧录 / 复位） | **A** | ✅ 大致成立 —— 但前提是**真板 + 探针（ST-Link 等）真的接在这台机器上**，且工具链已装 |
| 让插件**读真板信号 / 真机在环** | **C** | ✅ 成立，且这是"硬件在环"的正解 |
| 让**固件本身跑起来** | **B** | ⚠️ **反向的** —— B 是**不碰硬件**、用仿真器替代硬件 |

★ 更要紧的一句：**做完 ABC，插件仍然不是 CubeMX / CubeIDE 的替代品**，而是
**把它们串起来 + 让接线关系参与校验**。它不会因为 ABC 做完就"什么硬件都能驱"：

- **受外设建模范围限制**：我们现在的虚拟设备是 I2C / USART 级别的模型。
  真板上若跑 SPI / ADC / 定时器 / DMA，要在 B 里仿真就得**逐个外设建模** —— 这正是 B「很大」的原因。
- **受引脚映射表限制**：虚拟 `portId` ↔ 真板丝印的对应，需要**该型号的引脚定义**（见 §3.2）。
- **真机是墙钟**：真机在环不能像虚拟时钟那样加速 —— 与联网设备同一个坑（见 `docs/07`）。

⇒ 一句话：**ABC 做完得到的是"能对着真板做在环验证"的工具，而不是"通用硬件驱动框架"。**

## 1. 当前能力边界（准确版，别记错）

```
hw_run_simulation → 起一个 **Python 进程** → 挂 I2C shim（smbus / RPi.GPIO）
                  → 虚拟时钟可加速
                  → ⚠️ RPi.GPIO.input/output **故意抛 NotImplementedError**（v1 只覆盖 I2C）
```

- **模拟的是「宿主机上的 Python 程序」**，不是 MCU 固件。
- 全仓搜 `stm32|cube|CubeProgrammer|openocd|烧录|串口|esptool|platformio`：
  **命中全是文档引用**（引自智座项目自己的 `烧录与PIR接线操作指南.md`、`platformio.ini`），
  **没有一行是能力实现** ⇒ **现在完全不能驱动 STM32Cube**。
- ✅ 但**装配层是通用的**：摆器件 / 连线 / 电压·方向·I2C 上拉校验 **对 STM32 一样适用**。

## 2. 三条线的范围与前提

### A · 调用 Cube 工具链（生成 / 编译 / 烧录 / 复位）

| | |
|---|---|
| **目标** | 插件能调 CubeCLT / CubeProgrammer / CubeMX 的 CLI：生成代码 → 编译 → 烧录 → 复位 |
| **前提** | ① 本机装了对应 CLI（**待核实**：`STM32_Programmer_CLI.exe` / `STM32CubeMX` / `arm-none-eabi-gcc` 在不在）② 明确目标板与工程路径 |
| **可复用** | `subprocess` 服务**已在 `inject` 里** ✓（现在用它跑 Python）；工具注册与 HTTP 路由的既有形态 ✓ |
| **要新增** | 一个工具链适配器（探测 CLI 路径 → 统一接口）+ `hw_stm32_*` 工具 + 面板按钮；**构建产物与日志要能回看**（不是"点完就没") |
| **工作量** | 中 |
| **验证方法（必须实跑）** | 用一个**最小闪烁工程**实跑：生成 → 编译出 .elf/.bin → 烧到真板/或至少 CubeProgrammer 的 dry-run → **贴出退出码与日志** |

### B · 固件本身在仿真里跑（QEMU / Renode 级）

| | |
|---|---|
| **目标** | 固件（.elf）在仿真 MCU 上执行，外设行为由我们提供 |
| **前提** | 引入 MCU 仿真器（Renode/QEMU）+ **外设模型**（GPIO/I2C/USART 的时序与寄存器语义） |
| **可复用** | 装配/连线/校验层、虚拟设备抽象、虚拟时钟的既有设计 |
| **要新增** | 仿真器集成 + 外设桥（把仿真器的 I2C/USART 接到我们的 `VirtualDevice`）+ 断点/日志回读 |
| **工作量** | **很大**（这不是"调 Cube"能解决的 —— Cube 不做指令级仿真） |
| **验证方法** | 一个已知固件在仿真里跑出预期串口输出；同一固件在真板上**输出一致**（对照才算过） |

### C · 真机在环（虚拟装配 ↔ 真板）

| | |
|---|---|
| **目标** | 场景里连的线**对应到真板引脚**；真板读数回采进场景（像现在的 PIR 遮挡那样沿**实际接线**传导） |
| **前提** | 真板接在这台机器上（USB）+ 烧录链路（A）+ 串口/回读链路 |
| **可复用** | ★ `hw_set_occlusion` 的**读数来源自实际接线**这一套语义（接错脚就什么都不发生）—— **真机在环应当沿用同一条纪律** |
| **要新增** | 串口/USART 通道 + 引脚映射（虚拟 `portId` ↔ 真板丝印）+ 时序对齐（真机是**墙钟**，与虚拟时钟解耦 —— 与联网设备同一个坑） |
| **工作量** | 中~大 |
| **验证方法** | 拔掉一根线 / 接错一个脚，**场景里的读数必须跟着变错** —— 对得上才算真在环 |

**依赖顺序**：A 是 C 的前置（要烧录才能回读）；B 与 A/C 相对独立。

## 3. 开工前必须先做的两件小事（都便宜，且现在就成立）

1. **核实本机有没有 STM32 工具链** —— ✅ **已核实（2026-10-14），结论是：没有**：

   | 工具 | 结果 |
   |---|---|
   | `STM32_Programmer_CLI` / `.exe` | ✗ 不在 PATH |
   | `STM32CubeMX` | ✗ 不在 PATH |
   | `arm-none-eabi-gcc` | ✗ 不在 PATH |
   | `openocd` | ✗ 不在 PATH |
   | `make` | ✗ 不在 PATH |
   | `%ProgramFiles%\STMicroelectronics` | ✗ 目录不存在 |
   | `%ProgramFiles(x86)%\STMicroelectronics` | ✗ 目录不存在 |
   | `%LOCALAPPDATA%\Programs\STM32CubeMX` | ✗ 目录不存在 |

   ⇒ **A 线在本机无法开工**，卡在"先装工具链"这一步（**装什么、装哪一版，需要用户确认**：
   CubeCLT 就够，还是还要 CubeMX / CubeIDE）。
   ⇒ B 线不依赖这个（Renode/QEMU 是另一套），C 线依赖 A。
   ⚠️ 这条**必须写下来**：否则几个月后会重新问一遍"为什么 A 没动"。

2. **往 `library.ts` 加 STM32 型号（引脚定义）** —— 这**不需要 Cube**，不需要真板子，
   现在就能做：加了以后就能在 3D 里摆 STM32、按真实丝印连线、让校验器查电压/方向/上拉。
   ⇒ **"先能摆能连能查错" 与 ABC 三条线是解耦的**，可以先行。

## 4. 顺手记下的两条纪律（别在 ABC 上重犯）

1. **失败要可见**：工具链调用失败不能只打印"完成" —— A 的第一步就该定"退出码非 0 一定报错并给日志"。
2. **别把"能调起 CLI"当成"功能做完了"**：本项目的失败族里已经有过
   `ok:true ≠ 效果发生`（Promise 恒真那次）。ABC 三条的每条**都写了验证方法**，就是为了这个。
