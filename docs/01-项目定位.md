## 1. 一句话定位

> **一个项目级硬件在环（HIL）仿真沙盒**：用户在 3D 场景里拖拽真实硬件、连线、热插拔；DS 在同一场景里实时感知拓扑并能反向操作；**用户的真实项目代码，语义等价地跑在虚拟硬件上**。

差异化不在「3D 看硬件」（`dsh-3d-model-viewer` 已占位），而在**「代码真的跑起来了」**。

## 2. 双主线（保留，不改）

| | 主线 A：人机协作感知（**地基**） | 主线 B：项目级硬件仿真（**壁垒**） |
|---|---|---|
| 定义 | 用户和 DS 在同一 3D 场景里协作并互相感知 | 项目代码语义等价地跑在虚拟硬件上 |
| 组成 | 3D 场景 + 事件桥 + 状态 SSOT | 虚拟时钟 + 行为模型 + Shim/IPC |
| 独立价值 | ✅ 成立 | ✅ 成立（但依赖 A 的状态） |
| 卡住的后果 | 项目不成立 | A 仍可交付，失去壁垒 |

**保留理由（复核后仍然成立）**：砍掉 A 就退化成「3D 展示 + 报价」，与既有插件重叠；砍掉 B 就只剩一个能连线的沙盒，无壁垒；两条都砍则项目不成立。

## 3. 对设计文档的三处实质性修正

> 这三处不是文字润色，是**架构层面必须改**的地方。全部由实测得出。

### 修正 1 ★：不是两个 realm，是**三个**

文档 §1.0 / §4.1 的世界观是「DSH 宿主(JS) ↔ 项目进程(Python)」。**实际是三个执行域**：

```text
①  宿主 Node 进程        插件 host 半
   ├─ AssemblyState（SSOT）        ← 唯一真相
   ├─ VirtualClock + 设备行为模型
   ├─ BridgeServer（TCP 服务端）
   └─ 工具注册（DS 可见）
        ▲                              ▲
        │ ctx.webServer 路由           │ TCP + token（JSON-RPC/NDJSON）
        │ （HTTP/WS）                  │
②  浏览器                 ③  项目进程 Python
   插件 client 半               shim（仅代理，无硬件语义）
   Three.js 场景 = ① 的投影     用户项目业务代码
   交互 / 拾取 / renderViews
```

**后果**：
- 文档 §1.0 表格里「3D 联动：**直接**（同一进程）」这一格是**错的**——在真实宿主上是跨域 RPC。
- **但 SSOT 唯一性不但保住，而且更硬**：三个域里只有 ① 持有真相，② 是投影、③ 是代理。
- **SSOT 必须放 ①（宿主）而非 ②（浏览器）**，因为：BridgeServer 在 ①；面板关掉/切走后仿真必须继续跑；DS 的工具调用发生在 ①。
- 这一条其实与文档 §4.2.4 的原则「**场景是状态的投影，不是状态的副本**」完全一致，只是文档没把域边界点出来。

### 修正 2 ★：`tick()` 与 3D 渲染必须解耦

文档 §5.1 闭环把第 ⑦ 步写成「3D 场景实时渲染 [JS 内核]」，暗示 tick 直接驱动渲染。

**这在真实宿主上会打死链路**：`advance(1.0)` 在 `step=1ms` 下是 **1000 次 tick**。若每次 tick 都推一帧场景数据过浏览器 RPC，一次 `sleep(1)` 就是 1000 条消息 × N 设备。

**改法（写死为铁律）**：
> **虚拟时钟 tick 只写 SSOT；场景按显示节奏采样 SSOT（或按事件节流推送），绝不逐 tick 推送。**

两种模式分别处理：
- `accelerated`：tick 全速跑完，只推**首末状态 + 关键事件**（供回放/报告）
- `realtime`：tick 按真实节拍推进，场景按 `requestAnimationFrame`（§4.2.1 已要求按需渲染）采样

### 修正 3 ★：`advance()` 的时间片循环会**饿死宿主自身**

文档 §7.4 的 T4 只讨论「精度不够」。**真正的风险更靠前**：

```ts
advance(dt) {
  const target = this.now + dt
  while (this.now < target) {        // ← 同步忙循环
    this.now += this.step
    for (const dev of this.devices) dev.tick(this.step)
  }
}
```

`advance(1.0)` = 1000 次同步迭代。这个循环跑在**宿主 Node 的事件循环**上——期间 DSH 自身（会话、UI 通信、其他插件）**全部停摆**。多设备或大步长下会明显卡顿甚至误判为死机。

**改法（写死为硬要求）**：
> **`advance()` 必须在时间片循环中周期性 `await` 让出事件循环**（按墙钟预算），且预算可配；`accelerated` 模式必须跳过空闲区间，不得退化为暴力步进。

> **落地修正（步骤①实测）**：让出预算不是「每 N 片」而是**按墙钟毫秒**——
> 这样「算得快就不让出」（T5 不受损）、「算得久就让出」（T6 得到保证）。
> 跳空也不是「事件优先队列」，而是设备以 `nextEventIn()` **声明可跳空**；
> **只要有一台设备返回 `null`（需要每片）就绝不跳空**，因为积分型模型（BME280 漂移）
> 的结果与片数相关，跳空会改变结果。

§7.4 的 T1–T5 判据**保留**，但需**新增 T6**：

| 判据 | 通过标准 |
|---|---|
| **T6（新增）** | 单次 `advance(10.0)`（step=1ms，1 台设备）期间，宿主事件循环阻塞 **p95 < 5ms、max < 50ms**；即宿主心跳在仿真中不掉线 |

> **★ 判据为何盯分位数而非 max（已实测，详见 `02-步骤①-虚拟时钟内核.md`）**：
> 关闭让出时阻塞随总耗时线性增长（**1022ms 的推进就阻塞 1022ms**）；
> 打开让出后 **p50 精确跟随让出预算**，但 **max 有一个 ~16ms 的环境地板**
> （Node 定时器/GC 抖动），任何预算都压不下去 —— **不是时钟引入的阻塞**。
> 只盯 max 会把环境抖动误读成时钟缺陷，并让 CI 偶发红灯，正是本文档 §0.4
> 批评过的「用概率性行为验证确定性判据」。
>
> **默认让出预算取 1ms**：4ms 预算的 p95 已达 9.18ms、p99 达 15ms，几乎吃掉一个 60fps 帧；
> 1ms 预算的 p95 只有 1.19ms，代价仅 ~3% 总耗时。

## 8. 远程模型库与 STEP 管线（方向已定，但**不进 MVP**）

> 来源：并行会话转述的用户方向。**尚未写进设计文档**，因此只作为已记录的方向，不改变本期范围。

### 结论：方向**已确认**（用户 2026-10-07 确认，优先级不低），但**顺序要反过来**

> 用户确认：「它确实是已定方向，且优先级不低」。因此下面不是"做不做"，是"先做哪一半"。

#### 拆成两个独立阶段——成本与价值差很远

| | 阶段一：几何 | 阶段二：语义 |
|---|---|---|
| 产出 | glTF，组件**看起来对** | `schema/` 端口，组件**能用** |
| 输入 | 厂商 3D 模型（STEP/IGES） | 厂商符号/封装数据（**引脚名 + 编号**） |
| 依赖 | 需要 CAD 解析（重） | 纯结构化数据解析（轻） |
| 解锁什么 | 视觉正确 | **连线校验、地址冲突、仿真** |
| 与阶段二的关系 | **互不依赖** | **互不依赖** |

**只做阶段一 ⇒ 得到「好看但不能连」的组件**。而阶段二正是设计文档 §6.6 点名的「核心壁垒」，且不依赖任何 CAD 技术。

⇒ **建议：阶段二优先，阶段一后置。** 这与"优先级不低"不冲突——它只是把同样的优先级投在能解锁功能的那一半上。

#### 为什么仍**不**建议自建 STEP 解析器

1. **转换买不到功能。** 理由同上表。
2. **不能靠视觉反推端口。** 设计文档 v2 已明确**废除**「B 通道视觉标注」（从渲染图反推接口语义），原话是「有精确坐标不用却从渲染图反推 = 自我制造误差」。所以"转完自动认出端口"这条捷径**在设计上已被否掉**，不是没做。
3. **不划算。** Node 侧只能走 `opencascade.js`（WASM 约 30MB）。而在拿到引脚元数据之前，几何本来就可以先用占位盒——**现在正是这么做的**（4 个预置型号都是盒体）。

#### ★ 关键发现：目标厂商本来就有结构化元数据 API

2026-10-07 查证：**嘉立创EDA（EasyEDA）专业版有成体系的公开扩展 API**，且 API 里直接就有我们要的图元类别：

- `SCH_PrimitivePin` / `ISCH_PrimitiveComponentPin` / `ISCH_PrimitivePin` —— **引脚**
- `PCB_PrimitiveComponentPad` / `IPCB_PrimitiveComponentPad` —— **焊盘**
- `SYS_FormatConversion` —— 格式转换
- `SCH_ManufactureData` / `PCB_ManufactureData` —— BOM / 制造数据
- 开发指南另含「**命令行客户端**」（headless 化的希望所在）

**而这个厂商正是设计文档 §6.5 已经列为对接目标的那家**（「DigiKey、Mouser、LCSC、立创商城」）。也就是说：**BOM 的供应商适配层与模型库的语义来源，很可能是同一个集成**——不是两笔投入。

**兜底路径**：KiCad 的符号/封装格式是**开放且有文档**的（引脚由「图形表示 + 名字 + 编号」三元组定义），可完全离线使用，无需任何厂商关系。

#### 下一步：先做**可行性验证**（spike），不是开工建管线

**验证目标**：给定一个 LCSC 料号，产出**一条可用的 `HardwareModel` 记录**（端口名 + 编号 + 包围盒尺寸），且过程可重复、可脚本化。

**两条候选路径，先各验一条**：
- **路径 A**：嘉立创EDA/EasyEDA Pro 的 CLI / 扩展 API → 取符号与封装 → 抽引脚名与编号 → 生成 `schema/` 条目
- **路径 B**：KiCad 官方符号库（开放格式、离线）→ 同样抽取

**明确不在 spike 范围内**：STEP/IGES 解析、glTF 几何转换。几何继续用占位盒。

**准入判据**：能对**一个真实型号**端到端跑通并产出可用 schema，才谈排期。

#### 架构上不是新东西

② 正在建的「宿主 spawn Python 进程 + IPC」这套基础设施**可以直接复用**给厂商数据抓取/转换 worker。所以它不需要新架构，只是**多一个 worker 进程**。

#### 仍然建议：把这条正式入档

它源自用户口述 + 并行会话转述，**v4.1 设计文档里没有**。建议正式写进文档并给一个排期位置（M2 / M3），否则它会以「大家都知道要做」的形式长期悬着，反过来干扰范围控制（§9.2）。
