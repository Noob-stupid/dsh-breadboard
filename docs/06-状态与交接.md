### ★ ⑪ 的通道很容易找错（我第一遍就找错了，记下来免得再犯）

| 看起来像"发消息"的 | 实际是 |
|---|---|
| `commands.execute(agent, line, …)` | 文档原文 **"execute a known command *without sending it to the model*"** —— 斜杠命令，**不产生对话轮次** |
| `Session.append('user/message', …)` | 只往**日志**写事件，**不驱动 agent loop** |
| **`Agent.followup(input)`** | ✅ `send(input,'next-turn',true)` —— **就是"用户发消息、开新一轮"** |

前两个做出来的是「**看着像发了消息、其实模型没收到**」。出处 `packages/core/agent-loop/src/agent.ts`。

**两条硬约束**（都已实现并有测试）：
1. **绝不猜目标会话** —— 未指定 sessionId 且多会话时**拒绝并列出候选**。猜错会把消息发进别人的会话且无提示。
2. **拿不到 `agents` 就不注册路由** —— 且 `capabilities.chat` 缺省，前端据此**隐藏**输入框。
   ⚠️ `createChatSender` **总是返回函数**，所以入口必须判**服务**在不在、不能判 sender 在不在（判错了条件恒真）。

## 3. 关键决策（压缩版，理由见详细文档）

| 决策 | 一句话理由 |
|---|---|
| **三 realm**：宿主(SSOT) / 浏览器(投影) / Python(代理) | 文档原以为是两 realm；SSOT 必须在宿主（BridgeServer 在那、面板关了也要跑） |
| **tick 只写 SSOT，不逐 tick 推前端** | `advance(1.0)`=1000 片，逐片推会打死链路（已用节流验证：<100 条且累计量守恒） |
| **`advance()` 必须让出事件循环** | 同步忙循环会饿死 DSH 宿主本身（新增判据 T6） |
| **整数微秒为时间权威** | `0.001` 累加 1000 次浮点 ≠ 1.0，会让"确定性读数"多跳一格 |
| **原点 = 包围盒中心** | 旋转枢轴：角原点会让组件绕角甩出去 |
| **`size` 是 3D 包络，不是 PCB 封装** | 树莓派 PCB 1.6mm vs 含接口 17mm，用错会让板子陷进地面 |
| **端口位置用声明式 `portLayout`** | 手打 12 个坐标已出过错；规则让等距由推导保证（已验精确等价 3.5e-18） |
| **两处真相必除**：歧义两侧都抛错 | 既无位置也无规则⇒抛；两者都有⇒抛。加载期告警等于没告警 |
| **不采集厂商数据，改用户导入** | 条款约束的是**我们的**批量采集；用户自己下不在射程内 |
| **step.parts 是唯一可直连来源** | 公共 API + 免鉴权 + **每件都有 glbUrl**（GLB 免转换）+ 覆盖板卡模块 |
| **导入只收 partId，不收 URL** | glbUrl 由宿主从 API 取 ⇒ **SSRF 面为零** |
| **几何可由用户给，语义不能** | 端口语义跨两生态证明买不到，必须自产（DS 辅助读**原厂手册**） |
| **`tools`/`webServer`/`subprocess` 用硬 `inject`，不用 `ctx.get`** | 三者缺失都是**静默归零**（工具没注册/界面空白/仿真起不来）。硬依赖语义是"等到就绪再激活"⇒ 要么可用、要么不激活，**没有"激活了但功能悄悄没了"这一档** |
| **工具的 `parameters` 与 `output.schema` 是两套方言** | `parameters` 是给人写的源方言（属性内 `required: true`，由 `defineTool` 编译）；`output.schema` 是**已编译**形态（对象级 `required: [...]`）。我们不用 `defineTool`（零宿主依赖）⇒ **两边都必须自己写成标准 JSON Schema** |
| **不编造拿不到的字段** | 宿主刻意不暴露进程 pid（"provider-private"）⇒ `pid` 改为可选，拿不到就不打印。编个 `-1` 只会让日志**看着像诊断、实际是垃圾** |

## 5. ★ 智座（`D:\MAX_xiangmu`）：不适配 I2C 形态，但指向第二类虚拟硬件

**它是什么**：Flask + SocketIO + MySQL + Redis 的「智能选座与导航一体化系统」，带 APK。
**硬件**：ESP32 + 双红外/PIR/超声波 → **WiFi/HTTP 上报**给 Flask。
**Python 侧一行硬件调用都没有**（全项目无 `smbus`/`I2C`/`GPIO`/`serial`）⇒ **我们的 I2C shim 拦不到任何东西**。

**它要的三个接口**（这就是它的"硬件接口"）：
```json
POST /api/sensor/report           { "seat_id": 12, "ir_front": 0, "ir_back": 1, "device_id": "AA:…" }
POST /api/sensor/device/register  // 设备以 WiFi MAC 注册
GET  /api/sensor/device_config    // 设备拉配置（绑定座位/间隔/类型/ir_active_high）
```

**✅ 已完成**：做成插件里的**第二类虚拟硬件**（联网设备），4 个 `hw_network_*` 工具，
智座实测全链路通过（seat 6 `free → occupied → free`）。**详见 `docs/07`。**

**它揭示的结构性事实**（这条比智座本身重要）：
> 沙盒原来只做**协议虚拟化**（拦 I2C，设备被动等被读）；
> 智座需要的是**设备模拟器**（模拟联网设备的主动行为）。
> **同一命题换协议，而且简单一个量级。**

**⚠️ 它自带一个进程内模拟器**（`_build_sensor_simulator()`），但**绕过 HTTP/注册/配置下发** ——
与我们做的**互补而非重复**（它测状态机，我们测设备接入链路）。

**环境**：本机 MySQL(3306) + Redis(6379) **本来就在跑**，12 个依赖已装，**不需要 Docker**。
起法（从项目根）：`python app.py 127.0.0.1 5800`。

## 8. ESP32 模型：为什么用**手搓的**而不是真模型（已决策，勿反复）

step.parts 上唯一的真 ESP32 **开发板**模型是 `Arduino Nano ESP32`（2.8MB，已导入验证过）。
**但它只有 D0–D13 / A0–A7，没有 GPIO23 / GPIO27**，而智座（`D:/MAX_xiangmu`）的
固件与接线文档用的正是这两个脚 ⇒ **换真模型会让那两根线没有落点，接法不再忠实**。

⇒ **用回手搓的 DevKit 模型**（真机尺寸 55.25×12.60×28mm；PCB + 双排 15 针 + USB + WROOM 屏蔽罩 + 两个按键）。

★ step.parts 的覆盖边界（实测多次）：
  **有** 开发板 / 机械件 / PCB 封装 / Adafruit breakout（88 个）
  **没有** 面包板（`breadboard`/`solderless`/`protoboard`/`perfboard` **全 0**）、
          PIR（`pir`/`hc-sr501`/`motion sensor`/`infrared sensor` **全 0**）、
          BME280（`bme`/`bmp280` **全 0**）
