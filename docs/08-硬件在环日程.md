# 08 · 硬件在环日程（**终版**）

> **本文是终版**，合并此前的 STM32 / ESP32 / 固件在环三份散记。
> **状态：已排期，未开工**（P0 可立即开始；其余按期次推进）。
> 用户 2026-10-14 定的顺序与目的：**「根据 ESP32 处理做插件，STM32 是最后测验」**。

---

## 0. 目标，以及"怎么算成功"

**目标**：让插件从「虚拟硬件」走到「**真硬件在环**」，并**验证这套能力是不是通用的**。

★★ **验收判据（这就是用户要验的那件事）**：

> **接一块全新的板子 + 一套全新工具链（STM32），只写一个「适配器」就能跑通**
> —— **不需要改动装配层、校验层、工具注册、面板**。

- 若接 STM32 时**只动适配器** ⇒ 抽象做对了，「**硬件驱动基本都能搞**」这句成立；
- 若接 STM32 时需要**改核心**（连线校验、工具表、面板都要动）⇒ 抽象没做对，
  那时候"能搞"只是"又硬编了一块板子"。

⇒ **这就是把 STM32 排在最后的原因：它是验收，不是目标。** 拿它当第一块板做，
   会把"针对 STM32 的硬编"误当成"通用能力"。

## 0.1 与早先 ABC 的对应关系（同一套能力，重新分组）

用户问过「是根据之前提的 ABC 兼容路线吗」—— **是**。ABC 不是被推翻，而是被**重新分组**：

| 早先 | 含义 | 在终版里落到 |
|---|---|---|
| **A** | 调用工具链（生成 / 编译 / **烧录** / 复位）| **P3**（ESP32 烧录）；STM32 的那份 A ⇒ **P5** |
| **B** | 固件本身在仿真里跑（Renode / QEMU）| ⚠️ **移出主线**，见 §5 第 3 条（单列、按需） |
| **C** | 真机在环（虚拟装配 ↔ 真板）| **拆成两条**：**P1**（服务端回读）+ **P2**（串口回读）|

**三处实质变化**（都不是换路线，而是补上缺口）：

1. **新增 P4「适配器抽象」** —— 这是终版最重要的一条。
   没有它，P1–P3 只是"**又硬编了一块板子**"；有了它，P5（STM32）才能当**验收**。
   ⇒ 你问的"到时候硬件驱动是不是基本都能搞"，**判据就落在 P4**（见 §0）。
2. **B 降级为"按需"** —— 早先 ABC 把 B 与 A/C 并列，现在单列。
   理由：**仿真≠真机**（时序/中断/寄存器副作用都有偏差），它最贵，却**最需要真板来校准**，
   不该当第一步。
3. **顺序按"要件是否齐备"而非字母** —— ESP32 三要件齐（板/工程/工具链），
   STM32 三要件全无 ⇒ **ESP32 先行、STM32 收尾**。

**没变的**：A/B/C 各自的**验证方法全部保留**（真跑、贴退出码与日志、接错脚就该什么都不发生）。

## 1. 顺序，以及为什么

```
P0 加型号引脚定义（不需任何外部条件）
  ↓
P1 ESP32 · 服务端回读        ← 有板、有工程、有工具链 ⇒ 最快见效
P2 ESP32 · 串口回读
P3 ESP32 · 烧录
  ↓
P4 ★ 抽出通用「硬件适配器」接口   ← 真正的交付物
  ↓
P5 STM32 验收（最后）            ← 只写适配器，看能不能不碰核心
```

**为什么 ESP32 先行**（2026-10-14 实测，逐项当场验证过）：

| 要件 | ESP32 | STM32 |
|---|---|---|
| 板子 | ✅ 用户手上有（智座用 DevKit V1 / `board = esp32dev`）| ❌ 没有 |
| 工程 | ✅ `D:\MAX_xiangmu`（**已经在插件里建模过**）| ❌ 没有 |
| 工具链 | ✅ PlatformIO Core 6.1.19 已装（不在 PATH）+ `pyserial` 已装 | ❌ `STM32_Programmer_CLI`/CubeMX/`arm-none-eabi-gcc`/`openocd`/`make` **全无**，常见安装目录也不存在 |

★ **还有一处天然对接**（这是 ESP32 能当第一块试金石的关键）：
智座固件 `main.cpp` 里 `IR_SENSOR_A_PIN = 23`（ir_front）、`IR_SENSOR_B_PIN = 27`（ir_back），
与插件建模的 **`E4` = GPIO23、`E19` = GPIO27 完全一致**
⇒ 场景里的接线与真板的接线**说的是同一件事**，真机在环才有可能"对得上"。

## 2. 当前能力边界（准确版，别记错）

```
hw_run_simulation → 起一个 **Python 进程** → 挂 I2C shim（smbus / RPi.GPIO）
                  → 虚拟时钟可加速
                  → ⚠️ RPi.GPIO.input/output **故意抛 NotImplementedError**（v1 只覆盖 I2C）
```

- 现在模拟的是「**宿主机上的 Python 程序**」，**不是 MCU 固件**。
- 全仓搜 `stm32|cube|CubeProgrammer|openocd|烧录|串口|esptool|platformio`：
  **命中全是文档引用**（引自智座自己的 `烧录与PIR接线操作指南.md`、`platformio.ini`），
  **没有一行是能力实现** ⇒ **现在完全不能驱动任何 MCU 工具链**。
- ✅ **装配层是通用的**：摆器件 / 连线 / 电压·方向·I2C 上拉校验 —— 对 ESP32、STM32 一样适用。
- ✅ 已有的"真链路"是：真 Python 程序 → 真 HTTP → 真服务端 → 真数据库（**只有硬件那段是虚拟的**）。
  ⇒ 准确说现在是「**软件在环 + 虚拟硬件**」。

## 4. P4 的交付物：适配器接口草案

```
detect()   → 工具链在不在、板子在不在（探测失败要**说清缺什么**，不是静默返回 false）
flash()    → 调 CLI：**退出码 + 完整日志可回看**（不是"点完就没"）
read()     → 读数来源：串口 / 服务端 二选一（同一份接口）
reset()    → 复位
pinMap     → 虚拟 portId ↔ 真板丝印（如 E4 ↔ GPIO23）
```

**三条不可妥协的纪律**（本项目失败族的直接教训）：

1. **失败要可见** —— 工具链失败不能只打印"完成"；
2. **`ok:true` ≠ 效果发生** —— 曾经 `models.get(k) !== undefined` 因 Promise 恒真而全军覆没；
3. **读数来源自实际接线** —— 沿用 `hw_set_occlusion` 的语义：**没接上、接错脚，就什么都不该发生**。

## 5. 明确不做 / 边界（免得验收时混淆）

1. **不做"通用硬件驱动框架"** —— P5 通过只说明"**适配器抽象成立**"，
   不等于"什么外设都能驱"。**受外设建模范围限制**：现在只到 I2C/USART 级别，
   SPI / ADC / 定时器 / DMA 要逐个建模。
2. **不替代 CubeMX / CubeIDE** —— 我们是**把它们串起来 + 让接线关系参与校验**。
3. **「固件在仿真里跑」（Renode/QEMU）单列、按需做** —— ⚠️ **仿真≠真机**
   （时序、中断优先级、寄存器副作用都有偏差）⇒ 它的结论**必须用真板校准**，
   所以**不适合当第一步**（最贵，却最需要真板来验它对不对）。
4. **真机是墙钟** —— 真机在环不能像虚拟时钟那样加速（与联网设备同一个坑，见 `docs/07`）。
5. 不预置别人的项目与模型；第三方模型仍不分发。
