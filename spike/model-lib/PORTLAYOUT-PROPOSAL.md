# 提案：`portLayout` —— 用声明式布局取代手打端口坐标

> 提案人：session-40f8f716 ┃ 日期：2026-10-07 ┃ 落地归 `contracts/` owner（session-24ca6e69）
> 来源：模型库 spike 的收束结论（见 `FINDINGS.md` 第五轮）。**不依赖任何厂商数据。**

## 1. 为什么做

现状是 `HARDWARE_MODELS` 里**逐个手打 12 个坐标三元组**。代价已经兑现过一次：

> 两套原点约定混用（rpi-4b 按角原点、bme280/led-5v 按居中），导致树莓派 **4/6 个端口落在几何体外**，最远偏出 17mm。

而且用户明确希望「**接口位置能自动确定**」。厂商数据路线已证否（芯片封装 ≠ 模块封装），
**但"位置"恰恰是三个字段里唯一可以真正自动化的** —— 只要换成声明式规则。

## 2. 关键结论：三条规则可精确替代全部手打坐标（已实测）

用**契约真源**（`src/contracts/library.ts` 的 `HARDWARE_MODELS`）逐点比对：

| 型号 | 端口 | 规则 | 最大误差 |
|---|---|---|---|
| `rpi-4b` | 6 | `{ edge:'+z', pitch:0.012, count:6, inset:0.005 }` | 3.5e-18 |
| `bme280` | 3 | `{ edge:'-x', pitch:0.00254, count:3, inset:0.004, slots:[1,2,0] }` | **0** |
| `led-5v` | 3 | `{ edge:'+z', pitch:0.00254, count:3, inset:0.010, slots:[1,2,0] }` | **0** |
| `breadboard` | 0 | 无端口，无需规则 | — |

⇒ **规则不是近似，是精确等价。** 可以无缝替换。

## 3. 实验抓到的隐含约定 ★

第一次验证时 `bme280` / `led-5v` 差了 `0.00508`（= 2 × 间距）——**声明顺序不是几何顺序**。

契约现状：

```ts
bme280:  I2C (z = 0)   VCC (z = +pitch)   GND (z = −pitch)
led-5v:  SIG (x = 0)   VCC (x = +pitch)   GND (x = −pitch)
```

即 **「中间、右、左」**，不是「左、中、右」。

**这正是我们已经被咬过一次的那类隐含约定。** 两条路：

- **方案甲（零风险，推荐先做）**：规则带可选 `slots?: number[]`，显式声明「声明顺序 → 行内槽位」。
  不动现有 `ports` 数组顺序 ⇒ 不影响任何既有代码/测试。
- **方案乙（更干净，但要评估影响）**：把 `ports` 重排成几何顺序（`GND, I2C, VCC`），规则就不需要 `slots`。
  代价：`ports` 顺序若被别处依赖（演示装配、测试断言），需一并检查。

> 我倾向**先甲后乙**：甲立刻消除错误来源，乙留作整理。

## 4. 建议的字段形状

```ts
/** 一条边上的等距引脚排布规则（组件局部坐标，原点 = 包围盒中心）。 */
export interface PortLayoutRule {
  /** 所在边：行沿该边的方向展开（'+z'/'-z' 行沿 x；'+x'/'-x' 行沿 z）。 */
  readonly edge: '+x' | '-x' | '+z' | '-z'
  /** 该行端口数。 */
  readonly count: number
  /** 引脚间距（米）。默认 0.00254（2.54mm 排针）。 */
  readonly pitch?: number
  /** 距该边的内缩（米）。取 size 的相应半长即表示"行在板子中线"。 */
  readonly inset?: number
  /** 引脚高度：默认顶面下 0.1mm；'center' = 板厚中线；数值 = 绝对高度（米）。 */
  readonly height?: 'top' | 'center' | number
  /** 声明顺序 → 行内槽位（省略则 = 声明顺序，从左到右）。 */
  readonly slots?: readonly number[]

  // ── 结构性自检（见 §5）所需，可省略则用默认 ──
}

export interface HardwareModel {
  // ...existing...
  /** 端口布局规则。给出时 `ports[i].position` 由此**派生**；省略则沿用逐点书写。 */
  readonly portLayout?: PortLayoutRule
}
```

**派生规则**（`i` 为声明下标，`s = slots?.[i] ?? i`）：

```ts
沿边偏移 off = (s - (count - 1) / 2) * pitch
高度      y  = height === 'center' ? 0 : (height ?? size.y / 2 - 0.0001)
edge '+z' → { x: off,                  y, z:  size.z / 2 - inset }
edge '-x' → { x: -size.x / 2 + inset,  y, z:  off }
（'+x'/'-z' 对称）
```

## 5. 结构性自检（比逐点校验强）

现有自检只能验「每个点在盒内」。有了规则，可以验**规则本身合不合理**：

1. `count === ports.length`（或与声明的行内端口数一致）
2. **垂直方向**：`0 ≤ inset ≤ 垂直轴长度`（`z` 由 `+half` 单调走到 `−half`，**整条轴都可达**）
3. **沿边方向**：`pitch × (count − 1) ≤ 沿边轴长度`（整行**居中**，故只需"装得下"）
4. `order` 若非空，必须恰好是端口 id 的一个**排列**（无重复、无遗漏）
5. 派生出的点仍满足原有「在包围盒内」断言（回归保险）

> ★ **修正记录 —— 第 2、3 条原文都是错的，由 owner 实现时抓出：**
>
> · 原第 2 条 `inset ≤ 半长` **偏严**：会禁掉"行在板子中线"，而 **`led-5v` 正是 `inset = size.z/2`** ⇒ 被误判非法。
>   下界 `inset ≥ 0` 那半是对的（负值会从近侧穿出，与过大从远侧穿出**对称**，两侧都要拦）。
> · 原第 3 条 `pitch×(count−1) + 2×inset ≤ 沿边轴长度` **把两个正交方向塞进了同一个不等式**
>   —— `inset` 是**垂直方向**的内缩，沿边方向其实是居中排布 ⇒ `led-5v` 再次被误判（`0.02508 > 0.02`，而它坐标明明在盒内）。
>
> **是校验器第一次运行就把校验公式自己的 bug 抓了出来。**
> **逐点校验永远发现不了这件事：点都在盒内，逐点检查全绿，而规则是错的。**
> 这比任何"结构性校验有好处"的论证都有说服力 —— 因为它是**已发生的事实**，不是设想。

> 第 3 条（修正后）的价值仍在于：**能在"写规则"的那一刻拦住"行比板子还长"**，
> 而逐点校验只有跑完才知道。

## 6. 兼容性与影响（★ 已与 owner 约定的形态对齐）

**定位**：`portLayout` 是**作者时便利**，在模型库加载时**展开**成现有的 `ports` 数组。
`Port.position` 仍是**运行时唯一真相** —— 下游（L1 校验、快照、前端 `SceneSync`、包围盒自检、演示装配）**全部零改动**。

> 注：我方（提案人）与 owner 就这一形态**独立收敛到同一结论** —— 我原 §6 写的是「规则在构造静态表时一次求值，运行时零开销」，owner 写的是「加载时展开成 `ports`，`Port.position` 仍是唯一真相」。两者是同一件事。

### 6.1 两类形状：作者时 vs 运行时

```ts
/** 作者时端口：给了 portLayout 就不必写 position。 */
type AuthoredPort = Omit<Port, 'occupiedBy' | 'position'> & { readonly position?: Vec3 }

/** 作者时型号：允许省略端口坐标。 */
type AuthoredModel = Omit<HardwareModel, 'ports'> & {
  readonly ports: readonly AuthoredPort[]
  readonly portLayout?: PortLayoutRule
}
```

```ts
/** 展开：作者时 → 运行时。模块加载时一次完成，运行时零开销。 */
function expandModel(authored: AuthoredModel): HardwareModel

export const HARDWARE_MODELS: Readonly<Record<string, HardwareModel>> =
  Object.fromEntries(Object.entries(AUTHORED_MODELS).map(([k, m]) => [k, expandModel(m)]))
```

**关键性质**：展开后 `HardwareModel.ports[i].position` **类型仍是必填 `Vec3`**
⇒ **任何已有消费者都不需要知道 `portLayout` 存在。** 这是本提案改动面最小的原因。

### 6.2 各种情形（★ 已按 owner 实现修正：歧义一律**抛错**，不告警）

| 情形 | 行为 |
|---|---|
| 有 `portLayout`，端口未写 `position` | 由规则派生（**主用法**） |
| 有 `portLayout`，端口**也**写了 `position` | **抛错** —— 两种真相并存，拒绝加载 |
| 无 `portLayout`，端口**也**未写 `position` | **抛错** —— 拒绝静默落成 `(0,0,0)` |
| 无 `portLayout`，端口写了 `position` | 沿用逐点书写，行为与今天**完全一致**（向后兼容） |

> **修正记录（本提案原写「规则胜出 + 告警」，被 owner 驳回，理由成立）**
>
> `portLayout` 在**模块加载时**求值 —— **一条没人看的 warning 拦不住任何人**。
> 更关键的是：告警方案**承认歧义存在，却允许它继续存在**，只处理了一半。
> ⇒ 改为**对称抛错**：两种歧义（都有 / 都没有）一个都不放过。
>
> 静默落零、静默忽略显式坐标、坐标系混用、`1<<47` 得 32768、热重载报成功实则没换掉 ——
> **都是"看起来正常、实际全错"那一族。在加载时炸，比在画面上看着不对再回头查，便宜一个数量级。**

> **★ 附带实证**：owner 实现时发现原方案里那条"结构校验"公式**本身有 bug** ——
> `pitch×(count−1) + 2×inset ≤ 沿边轴长度` 会把 `led-5v` 判成非法（`0.02508 > 0.02`），
> 而它坐标明明在盒内。错因是我把 `inset`（**垂直方向**内缩）当成了沿边方向的边距。
> **是校验器第一次运行就把校验公式自己的 bug 抓了出来。**
> 逐点校验永远做不到这件事：**点都在盒内，逐点检查全绿，而规则是错的。**
> 这是「逐点 → 结构性」那次升级最纯粹的验证，且是**发生过的事实**，不是设想。

### 6.3 改动面

契约层：**+1 可选字段、+1 作者时类型、+1 展开函数、+1 条结构性自检**。
**不改任何已有消费者的代码**，不改 `Port` / `ComponentSpec` / `AssemblySnapshot` 的任何字段 —— 三 realm 契约形状一个字不动。

## 7. 这解决了什么 / 没解决什么

| | |
|---|---|
| ✅ 消灭出错的那类操作 | 手打数字、混用原点约定 —— **混用约定在规则下不可能发生**（位置由 `size` 派生） |
| ✅ 天然自洽 | 等距由规则推出，不靠人肉保证 |
| ✅ 自检升级 | 从逐点校验 → 结构性校验 |
| ❌ 仍不是"全自动" | 规则要人写。但它**是声明，不是测量** —— 一行规则 vs 六个三元组 |
| ❌ 不解决几何来源 | 3D 模型本身仍是占位盒（那是另一条线） |

**结论**：用户要的「接口位置能自动确定」，应当以**这个形态**交付 —— 在厂商数据路线上它不成立，在布局规则路线上它成立且已验证。
